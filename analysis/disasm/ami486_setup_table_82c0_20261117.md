# AMI486 ROM semantic follow-up — 82C0 table header and adjacent routines

Date: 2026-11-17  
Target: `ami486.bin` (64 KiB, Project134/main)  
ROM identity: SHA-256 recorded in `docs/PROJECT134_PLAN.md`: `91fd62ce3ccb0b79b42f5fd6c6a7262ed52824b8ade917181b8a12267fec003b`.

## Scope

This pass re-read the actual ROM bytes at `82A0–82EF`, `8300–83FF`, `8400–84CF`, `85C0–85FF`, `8E70–8F0F`, and `B500–B7CF`. It is a byte-level cross-check of the previously reported Setup-record path, not a claim that all of these ranges are semantically closed.

## Confirmed byte observations

### 1. Header / pointer region at 82C0

Little-endian words from the ROM:

| Offset | Word | Offset | Word |
|---|---:|---|---:|
| 82C0 | 0000 | 82C2 | 0000 |
| 82C4 | 19A3 | 82C6 | 0000 |
| 82C8 | 0000 | 82CA | 19A3 |
| 82CC | 19A2 | 82CE | 19A2 |
| 82D0 | 19A3 | 82D2 | 0000 |
| 82D4 | 19A3 | 82D6 | 0000 |
| 82D8 | 19A3 | 82DA | 19AB |
| 82DC | 19A5 | 82DE | 19AD |
| 82E0 | 19A7 | 82E2 | 19AE |
| 82E4 | 19A9 | 82E6 | 19AF |

These are ROM-resident initialized words, not evidence of runtime writes. The repeated `19A2/19A3` values point into the mixed data/table region previously identified around `19A2–1A8E`. The layout is consistent with a header plus pointers/limits and a sequence of near offsets, but the exact field boundaries and semantic names remain unproven.

### 2. Record-walk code at 8300 and 83B0

The two visible entry sequences share the same structural pattern:

- `8300`: `53 E8 02 00 5B C3` — short wrapper: save BX, call the following helper, restore BX, return.
- `8306` onward begins a second routine and references the word at `82C6` through a CS override (`2E 8B 1E C6 82`).
- `83B0` begins a second copy/variant of the record-walk sequence and also reads `CS:[82C6]`.
- Both walkers inspect record bytes at offsets `+1C`, `+1D`, and `+1E`, advance BX by `20h`, and use a status/termination byte at `+1E`. This confirms a 32-byte record stride in this path.
- The loop contains a test of bit 7 of a record byte (`F6 C4 80`) and advances over records while the byte at `+1E` is nonzero.

The exact meaning of fields `+1C/+1D/+1E`, and whether the two entry points are intended as independent walkers or wrappers for distinct record classes, remains open pending a complete control-flow decode and caller analysis.

### 3. Consumer at 8400–84C3

The routine beginning at `8400` is a multi-stage consumer of the Setup metadata:

- It tests a flag byte at `CS:[8280]` (`2E F6 06 80 82 40`) and branches around the main path when the flag is not set.
- It selects several embedded strings/messages via near offsets and BIOS-style far calls through a pointer held in the stack frame.
- It iterates a table in four-byte steps (`83 C6 04`), compares a current index against the bound at `CS:[82C2]`, and dispatches/continues according to the comparison.
- It reads per-entry bytes at `+1` and `+2`, combines/masks them, and emits a value through the helper at `0C80h` (the exact I/O/service meaning is not assigned here).
- The code therefore supports the earlier observation that the consumer treats a selected metadata array as four-byte records. It does not yet establish that every structure in `82C0–82E6` is itself a four-byte record array.

### 4. Cross-reference at 85D6

The sequence at `85D6` reads `CS:[82B0]`, decrements it, uses it to index a word table at `CS:[82CA]`, and then loads another word from the selected record. Nearby branches also read `CS:[8280]` and `CS:[8284]`.

This establishes that `82CA` is used as an indexed near-pointer/table base in this path, while `82B0` supplies a count or last-index-like value. Whether the value is a count, maximum index, or sentinel-adjusted count must be resolved from all writers and callers.

### 5. Data region B500–B7CF

The region is predominantly Setup UI data, not executable code:

- `B500–B50F` begins with compact control/limit bytes.
- `B510–B55F` contains a monotonically increasing byte sequence `00–53`.
- `B560` onward contains NUL-terminated option labels such as Reserved, Disabled, Enabled, Absent, Present, Low, High, Off, On, No, Yes, Setup, Always, Video, Main, Both, Slow, Normal, Fast and clock/timing labels.
- `B7B0` begins a compact table of little-endian near offsets (e.g. `740C`, `2EB4`, ...), likely associated with the immediately preceding option strings or menu descriptors. This table requires separate cross-reference validation before assigning entries.

## Current conclusions

1. The Setup path uses 32-byte records in the walker at `8306/83B0`.
2. A separate consumer at `8400` iterates four-byte records.
3. `CS:[82C6]` is directly read by both walkers; `CS:[82C2]` is used as a bound by the consumer; `CS:[82CA]` is used as an indexed word-table base by code at `85E6`.
4. The header fields are ROM initialized. No runtime initializer/writer has yet been proven for `82B0`, `82C0–82E6`, or the referenced data at `19A2–1A8E`.
5. The earlier blanket description “82C0–82C2 define the range of four-byte records” is too broad: the byte-level evidence shows several distinct words in the `82C0–82E6` region with different observed uses. Keep the fields individually unnamed until all references are resolved.

## Next analysis actions (non-circular)

1. Build a complete read/write cross-reference for every address in `82B0–82E6`; distinguish ROM constants from RAM variables and runtime writes.
2. Decode `19A2–1A8E` as data and identify exact targets for `19A2`, `19A3`, `19A5`, `19A7`, `19A9`, `19AB`, `19AD`, `19AE`, and `19AF`.
3. Finish CFG/caller analysis for `8306`, `83B0`, `8400`, and `85D6`; do not infer semantics from UI strings alone.
4. Correlate the confirmed accesses with the exact ALi1429 emulator model and runtime port trace only after the BIOS-side access sequence is known.

## Evidence limits

This note records bytes and direct instruction-level references visible in the inspected ranges. It does not claim a successful runtime trace, complete code/data classification, a verified ALi1429 register mapping, or a finished semantic disassembly of the ROM.
