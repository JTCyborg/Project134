## Important interpretation limits

This is a **linear decode**, not a claim that all bytes are executable instructions. The ROM contains data tables, strings, vectors, padding and embedded structures. Linear decoding through those regions naturally produces plausible-looking but semantically meaningless instructions.

The existing entry-point listings remain separate historical views:

- `ami486_reset.disasm.txt`: begins at `E05B`, continues through `FFFF`.
- `ami486_post_entry.disasm.txt`: begins at `D604`, continues through `FFFF`.
- `ami486_branches.disasm.txt`: selected branch and alternate-entry excerpts.

These are not concatenated with the new master listing. Alternate entry points can decode the same bytes differently; keep those views distinct.

## What remains for semantic completion

The byte-complete master linear listing is done. A complete *semantic* disassembly still requires:
1. Marking code versus data ranges.
2. Building a control-flow graph from reset, POST and interrupt/vector entries.
3. Recording overlapping instruction streams and alternate entries.
4. Identifying option-ROM/embedded payload boundaries and table formats.
5. Tracing indirect calls/jumps and runtime-patched vectors.

Do not call this work finished merely because the linear listing reaches `FFFF`; semantic classification is a separate stage.

## Reproducibility

Workflow: `.github/workflows/ami486-full-disasm.yml`. It checks the ROM length, computes SHA-256, generates the linear listing, verifies exact coverage, writes the manifest and commits both output files. A change to the ROM or disassembly index reruns the workflow.
